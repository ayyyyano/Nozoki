# 备份与恢复

Nozoki 有两类“备份”，用途不同，不能互相代替：

| 方式 | 适合什么 | 做不到什么 |
| --- | --- | --- |
| 后台「数据导出」生成的 JSON | 换一个部署时搬“看板长什么样”：站点外观、模块、链接、行情、来源地址 | 拿不到登录密码；默认不带来源密钥；不能恢复采集历史 |
| 完整数据库备份（D1 / SQLite） | 连历史数据和加密凭据一起搬迁，或防止误删 | 不能直接当配置文件导入后台 |

**一句话结论**：配置 JSON 只负责“设置”；想把历史、密钥也一起恢复，必须另外备份数据库，并且把对应的密钥保管好。

## 先看懂：东西都存在哪里

| 内容 | 存在哪里 | 配置 JSON 能带走吗 |
| --- | --- | --- |
| 站点名称、外观、时区、日程 | 共享配置 | 能 |
| 模块开关、可见范围、字段权限 | 共享配置 | 能 |
| 链接、行情标的 | 共享配置 | 能 |
| 来源地址、类型、刷新间隔、字段映射 | 共享配置 | 能 |
| 已上传的背景图 | 共享配置（随文件附带） | 能 |
| 来源密钥（API Key、Management Key 等） | 数据库，加密保存 | 只有勾选「包含凭据」才以明文导出；导入到新部署时会用新部署的密钥重新加密 |
| 来源的「已批准」状态和能力验证结果 | 数据库 | 不会。导入后需要逐个重新测试并批准 |
| 余额观测、每日用量、Codex 日用量 | 数据库 | 不会。勾选「包含采集历史」只是归档，任何部署都无法导入 |
| 快照、采集记录、审计日志 | 数据库 | 不会 |
| 管理员邮箱和密码、`AUTH_*`、`INTEGRATION_*` 等密钥 | Worker Secret 或 Node 环境文件 | 不会，需要在新部署手工配置 |
| 定时任务、D1 绑定、域名 | 部署配置 | 不会，需要按部署方式重新设置 |

导出文件里含有站点地址和权限信息，请像对待密码一样保管。

## 场景一：只换部署，搬设置就够了

适合：只是换个域名或重新部署，来源密钥可以重新填，历史数据可以从新开始积累。

1. 在旧站后台打开「数据管理 → 导出配置」。**不要**勾选「包含凭据」和「包含采集历史」。
2. 在新站登录后台，打开「数据管理 → 数据导入」，选择刚下载的 JSON。
3. 预览无误后选择「导入到草稿」，再点「保存配置」。
4. 到「来源接入」把需要采集的来源逐个**测试并批准**。

导入后：站点外观、模块、链接、行情、来源地址都会回来；已保存的来源密钥不会回来，需要重新填写；图表和用量会从新部署重新开始记录。

## 场景二：连来源密钥一起搬

适合：不想重新逐个申请或填写 API Key。

**先满足两个条件，否则导入会失败：**

- 旧部署能解开已保存的密钥，也就是说运行环境里有对应的来源加密密钥。如果旧站没有配置这些密钥，勾选「包含凭据」时后台会提示“无法解密全部来源凭据”。
- 新部署要先配好自己的 `INTEGRATION_ENCRYPTION_KEY` 和 `INTEGRATION_KEY_VERSION`（见[环境变量](/operations/environment.md)）。没有它们，保存带密钥的导入配置会被拒绝，提示凭据密钥不可用。

步骤：

1. 在旧站导出配置，勾选「包含凭据」。如果还要导入，就**不要**勾选「包含采集历史」。
2. 文件含明文密钥，请通过安全渠道传输；导入完成后立即删除本地文件。
3. 在新站选择该文件。预览里会列出需要验证的来源，按提示逐个「验证并继续」：
   - 验证通过的来源，密钥会在保存配置后生效；
   - 验证未通过的来源，会保留地址但不迁移密钥，需要你手动补填。
4. 保存配置，再到「来源接入」确认来源已批准、采集正常。

CLIProxyAPI 的身份密钥遵循同样规则。如果目标部署已有身份密钥，或来源标识发生变化，系统会拒绝覆盖，需要先核对现有来源。

## 场景三：完整恢复（含历史和密钥）

适合：服务器故障、换主机、需要把历史图表和已加密凭据原样恢复。请使用完整数据库备份，而不是配置 JSON。

**Cloudflare D1**：在 D1 控制台查看可用的 [Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) 时间点，或自行导出数据库。恢复前先确认目标数据库和时间点，并暂停会写入的服务。恢复数据库同样需要原版本的解密密钥。

**SQLite**：

```sh
pnpm db:backup:node /var/backups/nozoki/manual.sqlite
```

目标文件必须尚不存在。命令使用 SQLite 在线备份并执行 `quick_check`；单独复制主数据库文件可能漏掉 WAL 中的写入。恢复时停止网页服务与采集，把完整备份复制到新的数据路径，检查运行账号权限，并更新 `NOZOKI_SQLITE_PATH`。验证看板、登录和来源凭据后再恢复采集。

完整恢复还要注意：

- 把原部署的 `ADMIN_*`、`AUTH_*`、`INTEGRATION_*` 等 Secret 和环境文件一并恢复，否则可能登录不上或解不开凭据。
- 如果换了加密密钥，需要把旧密钥放进 `INTEGRATION_DECRYPTION_KEYS`，并参照[轮换来源加密密钥](/operations/security.md#轮换来源加密密钥)逐个迁移凭据。
- 恢复完成后再启动定时任务，避免重复采集。

## 「恢复全局默认设置」不是恢复备份

这个按钮会把站点、模块、日程、链接恢复为默认值，清除全部来源凭据和采集历史（余额观测、每日用量、Codex 日用量、采集记录与快照，对话框会列出待删行数）。删除不可恢复；腾讯默认行情会恢复启用，采集调度和登录状态保留。需要保留数据时请先导出。操作需要输入「重置」确认，确认后立即保存并生效。

## 常见问题

**勾了「包含采集历史」，为什么导入不了？**
这些数字绑定了每个部署内部的来源编号，只能作为归档离线查看。想恢复图表历史，请用数据库备份。

**导入后图表是空的、来源不采集？**
历史没有随配置 JSON 过来；另外导入后的来源默认未批准，需要到「来源接入」重新测试并批准。

**旧部署没有加密密钥，还能导出全部配置吗？**
只能导出不含来源密钥的配置。来源密钥不能以明文导出，也就无法用它在新部署恢复。

**只保存配置 JSON 够不够？**
不够。它还不含登录凭据、部署环境和采集历史。重要部署请同时保留数据库备份，并把密钥单独存放在密码管理器里。
